# Server push and shared AI safeguards

`push_and_ai_limits.sql` adds server-only tables with RLS and no anonymous/authenticated client grants. Web Push VAPID signing keys and the scheduler token are generated once and stored only in `server_secrets`; the frontend receives only the VAPID public key. Subscription encryption keys, endpoint addresses and signing credentials must never be logged or checked into Git.

Users explicitly enable browser notifications under Settings → Notifications. Browser permission is not requested automatically. A service worker receives encrypted push with the application tab closed, and notification clicks stay on the app's origin. Logout unsubscribes the device. Account deletion removes subscriptions and queued deliveries. Different devices must grant browser/OS notification permission independently; iPhone/iPad may require an installed Home Screen web app.

The server schedules daily study reminders, due-card alerts, streak alerts, Sunday digests, timetable reminders and newly completed notes using each account's synced timezone/preferences. Reminders use a bounded catch-up window, unique per-device/event IDs, leased delivery, three delivery attempts, a 10-minute push TTL, and cleanup of invalid/expired subscriptions. Push payloads do not include private lecture titles or transcript content. Provider/OS delivery is not an exact-time guarantee.

After deployment, run `node scripts/setup-push-scheduler.mjs` once against the project database. It enables Supabase `pg_cron`/`pg_net` and installs one named job invoking the fixed Render dispatcher every minute **only when a opted-in subscription exists**. Authentication uses a dedicated server-only token; the cron definition has no plaintext secrets. The dispatch function and transient HTTP request/response tables deny API-facing roles. This scheduler is required for reminders when the Render free instance is asleep. The API process also checks reminders each minute while running. No paid plan is configured.

Production AI routes use PostgreSQL quotas, not the legacy process-local test helper. Acquisitions serialize on a shared global row: 12 requests/minute and 300/day per verified user; 120/minute and 5,000/day globally; two active requests/jobs per user. Leases renew while active and expire after crashed instances. Processing jobs also acquire a permit and defer quota-blocked jobs without consuming their processing-failure attempts. Database safety-check failures return 503 rather than allowing unmetered AI access. These are request budgets, not precise token or dollar budgets.

The API now uses Firebase's public signing certificates to verify Firebase client ID tokens with a public project ID. It does not use a Firebase admin private key or acquire application-default admin access. Admin SDK mutations fail closed. During rollout it can extract the public project ID from legacy configuration; migrate Render to `FIREBASE_PROJECT_ID` and disable exposed historical service-account keys after verifying a real authenticated session.

Secret remediation requires explicit authorization. `rotate-database-secret.mjs` rotates only the checked `postgres` role, updates the ignored local environment using apply_patch, and prepares an ignored runtime record for the approved Render secret handoff. It never prints old/new connection secrets. Changing the shared database password affects other consumers of that password. Git history is not rewritten; disabling historical credentials is the protection against reuse.

The current Supabase project rejects SQL password changes with SQLSTATE `42501`. The attempted rotation restored the original local environment and removed its temporary handoff record; the exposed database password has **not** been rotated. Dashboard password entry/confirmation must be completed by the account owner, followed by updating every backend connection secret. Do not report credential remediation complete until that reset and a fresh connection check succeed.

Tests: `npm run test:push-limits`, `npm run test:persistence`, frontend `npm run test:push`. Set `RUN_PERSISTENCE_DB_TEST=true` to exercise actual PostgreSQL quotas, leases and push-outbox SQL in rolled-back temporary tables; no production application rows are modified by those tests.
